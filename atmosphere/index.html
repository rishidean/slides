The Dhaka problem · what we were doingSelf-paced

We went to Dhaka to build a jobs marketplace.

Kormo was Google's job marketplace for the informal sector: drivers, retail staff, delivery riders. Millions of seekers, thousands of employers, and almost no digital rails between them. First we had to learn how hiring worked.

github.com/rishidean/<harness-repo> · Teaching talk
The Dhaka problem · what we learnedSelf-paced

This is how you applied for a job.

You printed a CV, found a box, and dropped it in. A red drop box, a taped cardboard one, a wooden one behind a mall counter.

github.com/rishidean/<harness-repo> · Teaching talk
The Dhaka problem · the insightSelf-paced

The insight: a CV is just input.

Issue

Paper, at scale. Thousands of CVs in boxes; no structure, no search, no way to match a person to a job.

Insight

A CV is unstructured input. Parse it into a structured profile, and the whole market opens up.

Product

Scan or build your CV in Kormo; the parser turns paper into a profile. Jobs find you.

So we built the parser. The boxes became searchable profiles, and jobs started finding people. It worked — to a point.
github.com/rishidean/<harness-repo> · Teaching talk
The Dhaka problem · to a pointSelf-paced

The parser assumed every CV looked one way.

Real CVs in Dhaka didn't. Every mismatch became another special case — and the special cases never stopped. The software assumed it knew you, and asked you to bend.

This is the wound: prescriptive software, written once, for a world that won't hold still.
github.com/rishidean/<harness-repo> · Teaching talk
The Dhaka problem · even todaySelf-paced
Build it today, and you'd still be stuck.

Put a modern agent on it — airborne mode, the harness from the recap. Parts get better: the model reads messy CVs a rules engine never could. But it still guesses from scratch every time, forgets between sessions, and can't show its work. Same wound, better model.

Why airborne isn't enoughSelf-paced

Three cracks in airborne-only.

01 · Memory

It never learns

Every session starts cold; corrections evaporate. The system is smart, but no smarter on day 100 than day 1.

02 · Observability

Can't audit a guess

No single front door. You can't reproduce, verify, or trust what you can't see it do.

03 · Cost

Full price, every time

Every action hits the model. Cost scales with usage; usage is exponential. You're penalized for success.

github.com/rishidean/<harness-repo> · Teaching talk
The cost crack · day 100Self-paced

Same exponential usage. Two very different bills.

Airborne · cost tracks usage Adaptive · where we're going

Airborne pays the model full price for every action, forever; cost rides the usage curve.

The Day 100 Problem: the system is as slow and expensive on day 100 as on day 1, because it learned nothing structural. The pink line is a different machine: it pays only for what's new. A pattern costs model calls until it's learned; repeating it is free.

You can't draw the pink line from the air. Building the machine that draws it is the rest of this talk.

To reach orbitSelf-paced

What a self-maintaining system needs.

01
Heals crack 01 · memory

Remember

A place to keep what it learns — knowledge sorted by how fast it changes, so it can be edited, audited, and trusted.

02
Heals crack 02 · observability

Observe

One front door for every action, so the system can watch the user work — every decision logged, replayable, auditable.

03
Heals crack 03 · cost

Compile

A way to graduate repeated, confirmed behavior — measured against a stability threshold — out of the model into fast, free, deterministic code.

One need per crack, one invention per need: layered context to remember, the pipeline to observe, progressive determinism to compile.

Invention 1 · the setupSelf-paced

"Remember" isn't one thing.

Say "take me to the airport." Four different kinds of knowing are in play — and they change at four different speeds.

What

What things are

A trip has an origin, a destination, a time. Almost never changes.

Why

How it should behave

Never spend money without confirming. Changes rarely, and deliberately.

How

How the work flows

Are we planning the trip, or booking it right now? Changes per task.

Who

What's true about you

Home is San Francisco; your airport is SFO. Changes all the time.

Cram all four into one prompt and they blur together. Store them in layers — sorted by how fast they change — and each can be edited, trusted, and compiled on its own schedule.

rishidean.com/layered-context · Teaching talk
Invention 1 · the navigation systemSelf-paced

Layered context: four layers of memory,
at four densities.

What

Ontology

The world model: the objects, their shapes, what operations are legal. The physics of the agent's world.e.g. a trip = origin + destination + time

Crystallized · schema
Why

Character

Identity, norms, guardrails. What makes the same world model feel like a chief of staff vs. a code reviewer.e.g. never book without confirming

Solid · config
How

Workflow

The active process: what's legal and what's preferred right now. "Let's plan" vs. "just do it" selects one.e.g. planning mode vs. booking mode

Fluid · process
Who

Memory

This user, right now: a living model of their intent, not a vector store of old chats.e.g. home: SF → nearest_major_airport = SFO

Volatile · retrieved

Stop writing specs for humans. This machine-readable corpus is the source of truth: solid at the top, molten at the bottom.

Invention 2 · the flight computerSelf-paced
Hero · execution pipeline

The execution pipeline: one door, three routes, one writer.

The resolver's choice is just memory: a compiled rule if one exists, a nudged guess if a pattern is forming, a cold guess if it's brand new. Every directive enters one door and exits through one writer — you can only adapt to behavior you can see.

github.com/rishidean/<harness-repo> · Teaching talk
Invention 2 · continuedSelf-paced

The seam: a rule and a guess are interchangeable.

Because both paths produce identical writes, you can run them side by side and diff the results. When the rule matches the guess every time, swapping it in changes nothing downstream. That's the equivalence check: the seam that makes compilation safe. An anchor — a check that can't argue back.

Hero · lifecycle bar (recurs in demo & frontier)

Progressive determinism.

User behavior is the source code; the learning loop is the compiler. A pattern only crosses the gate when it's repeated, confirmed, and stable past a threshold: the system earns its own determinism.

github.com/rishidean/<harness-repo> · Teaching talk
One loopSelf-paced

The air loop runs. The orbit loop closes.

Air · the harness loop

Plan → build → test → ship

Fast, tireless — and amnesiac. Every run starts cold, corrections die with the session, and the 401st request costs exactly what the 1st did.

Orbit · the flywheel

Observe → nudge → compile → free

Every run teaches the next. Corrections accumulate, stable patterns leave the loop as hard code, and the model stays aimed at whatever is still unknown.

Same harness underneath. The difference is the loop feeds back into itself: the pipeline observes → context remembers and nudges the next guess → determinism compiles → the pipeline runs faster → the model is freed for new unknowns.

Back to DhakaSelf-paced

So how would we build Kormo today?

1

One front door

Every CV — photo, paper scan, app form — enters the same pipeline, and every parse is logged.

2

The model reads the messy ones

A layout it's never seen gets a cold guess; a human confirms or corrects the parse.

3

Confirmed layouts compile

After enough confirmations, that layout becomes a rule. The next thousand CVs in that format parse instantly, for free.

4

The model stays on the frontier

Only genuinely new layouts ever reach it. The parser grows a rulebook shaped by Dhaka's real CVs — not our assumptions about them.

The 2019 parser asked people to bend to the software. This one bends to them, one compiled layout at a time. That's the wound, closed.

The inversionSelf-paced

The LLM is the compiler, not the runtime.

Today

LLM as runtime

You put a model on the process. It reasons about the same insertion order for the four-hundred-and-first time. Faster, but it never learned.

The inversion

LLM as compiler

It interprets the order it hasn't seen, a human validates, the system extracts the reusable logic into a deterministic path. The next order never touches the model.

The goal inverts too: use less AI over time. Measure success by the model calls you've eliminated.

Independent convergenceSelf-paced

Don't take my word for it.

The second-brain crowd

The vault becomes a graph

A raw note vault reads 2,000 notes to answer one question — full price, every time, no smarter on day 100. Their fix: a router, an index, edges. Retrieval compiled into logic; the model runs once, on what's left.

The agent-orchestration crowd

The workflow gets saved

A model drafts the fleet cold — full price. The run works, you confirm it, you save it — and it re-runs by name, deterministically, forever. Unknown → Observed → Compiled, in their own tooling, unnamed.

Different communities, different problems, same law: structure what's stable, and spend the model only on the unknown. They keep arriving here, one domain at a time.

The askSelf-paced

One process. 30 days.

Pick the single operation that reasons from scratch every time — the insertion order re-read for the four-hundredth time, the ticket triaged by hand, the weekly deck built from the same five sources. Don't aim for the Enterprise; aim for your first rule. The era of prescriptive software is ending, and the teams that build the graduation gate first win.
