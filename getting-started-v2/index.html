VIBE CODING
Prompt and iterate.

You chat, it generates, you eyeball the result and ship. No specs, no checks, nobody reads the code.

Fine for throwaways
AI-ASSISTED

You author specs and scaffolding. The system builds, verifies against acceptance criteria, and returns evidence. Quality lives in the spec.

Where the 10× live

High-leverage teams don't just use agents to code; they build systems that govern how agents code.

ANATOMY · EPIC

Epic: durable intent, with a fence

HOW TO DEFINE ONE
NAMEa real word, permanent, no numbers
GOALwhat’s true when it’s done
SCOPEwhat’s in
CUT LISTwhat’s deliberately out, in writing

The cut list is the agent-critical part: an agent can’t tell a gap from a decision unless the decision is written down.

## EPIC: BOOKING  (next: fully decomposed)
goal:  rider requests and completes a ride
scope: destination, estimate, match, lifecycle
cut:   scheduling, in-app payment, driver app
 
## EPIC: EXCEPTIONS  (later: directional)
goal:  the unhappy paths get handled
notes: cancellation, no-driver timeout…
// a fence: real, coming, not now

Specify the next epic fully; keep later epics directional. A future left unwritten is a future the agent builds early.

PREFLIGHT CHECK · FIVE QUESTIONS

Five questions, asked before the sprint starts.

01
Can I name what demos? When this is done, what do I open, and what do I see?
02
Is everything written down? What is in scope, and what is explicitly excluded?
03
Is every condition observable? Could someone else check it without asking me?
04
Does it name its dependencies? What may the agent assume already exists?
05
Where does the result go? Which file records the outcome, and who writes it?

Any no is a decision you are about to delegate. The headline question is the invention test: what would the agent still have to invent?

slides.rishidean.com/getting-started
FAILURE MODES

Three ways a spec fails, and none of them looks like failure.

01
Scope lists only what is in. Nothing is excluded, so everything is permitted.
02
Acceptance describes intent. Fast, clean, and works cannot be checked by anyone.
03
Dependencies stay implicit. The agent builds on something that is not there.

None of these read as errors. That is why they survive review.

THE SECOND DRAFT

The first draft is for finding the blanks.

01
A peer marks what they would invent. Cheaper and faster than any review process you have.
02
An agent names what it would invent. Every guess it lists is a blank you can close.
03

A spec that has never been critiqued is a draft, whatever it is called.

THE INNER LOOP

RED doesn't stop the loop: it routes back to the Builder.

On RED, the verdict carries the actual failures — the Builder reads them, patches, and re-runs. Three attempts, then it stops. RED isn't an opinion — it's a failed assertion; the fix targets a fact, not a feeling.

RED → read failures · fix · re-run
The Builder
Write & fix
Builds the feature. On a RED return, reads the failures and patches the code.
→
run-qa
Verify
Lint · review · test. Returns one verdict — and the failures with it.
→
RED loops back ↑
GREEN exits → Document
Three attempts, then it stops. Still RED after the third try → mark the sprint ⛔ blocked and hand back to a human. Autonomous, never infinite.

THE ORCHESTRATORrun.sh

A few lines of bash, dead simple by design.

#!/usr/bin/env bash
# PEDAL outer loop. Dumb on purpose: all the intelligence is in the files it reads.
set -euo pipefail

MAX_TURNS="${MAX_TURNS:-4}"

for turn in $(seq 1 "$MAX_TURNS"); do
  if grep -q '⛔' docs/Roadmap.md; then
    echo "run.sh: a sprint is blocked (⛔). A human steps in here. See PROGRESS.md."
    exit 1
  fi
  remaining=$(sed -n '/## Sprints/,/## Current Status/p' docs/Roadmap.md | grep -cE '🔲|▶' || true)
  if [ "$remaining" -eq 0 ]; then
    echo "run.sh: every Booking sprint is done. Open the app and take the ride."
    exit 0
  fi
  echo "── Turn $turn: $remaining sprint(s) remaining. Launching a fresh session."
  claude -p "$(cat prompt.md)"
done

echo "run.sh: reached MAX_TURNS=$MAX_TURNS. Check docs/Roadmap.md for state."

The real file, from the harness tag.

DEBRIEF

What just happened.

02
The QA gate caught a real failure. In S3, repeated live-region text broke three test locators; the Builder fixed the test, not the product, and re-ran to GREEN.

THE ORCHESTRATOR · DECISIONS

Three decisions, and everything else is execution.

01
What runs next. Which sprint, in what order, and what it is allowed to read.
02
When to stop. A RED QA gate, a blocked sprint, or a spec that cannot be satisfied as written.
03
When to hand back. The moment a decision is missing, the loop stops rather than invents.

A loop that cannot stop is not a system. It is a bill.

THE PRIMITIVES

A few words to help speak the language.

Quick refresher Everything that follows is just some form of these terms.

Session
One run of Claude Code. Fresh memory every time. Nothing carries over.
Context window
The working memory a session holds at once. Finite. Fill it and quality drops.
CLAUDE.md
A context file Claude reads automatically at the start of every session.
Task tool
How a session hands a job to a subagent — and gets the result back. It's how run-qa calls its three agents.
Skill
A reusable procedure Claude can invoke by name — like run-qa.
Command
A saved prompt you trigger with a slash — like /review.
Subagent
A scoped helper for one narrow job. Often a cheaper, faster model.

PREFLIGHT CHECK · FIVE QUESTIONS

Five questions, asked before the sprint starts.

01
Can I name what demos? When this is done, what do I open, and what do I see?
02
Is everything written down? What is in scope, and what is explicitly excluded?
03
Is every condition observable? Could someone else check it without asking me?
04
Does it name its dependencies? What may the agent assume already exists?
05
Where does the result go? Which file records the outcome, and who writes it?

THE JUDGMENT LAYER

THE READINESS SCORE, TWO WAYS

A prompt asks; a typed call measures.

PROMPT AND PARSE

“Is this spec ready to build? Answer yes or no.”

You get a word. No calibration, no confidence, and a different word each time.
TYPED CALL

The spec goes in as state. The question comes back as a probability, with a confidence attached.

Thresholds live in your code, so the decision stays yours.

You are not asking the model to decide. You are asking it to measure, and deciding yourself.

The insight: a CV is just input.

Issue

Paper, at scale. Thousands of CVs in boxes; no structure, no search, no way to match a person to a job.

Insight

A CV is unstructured input. Parse it into a structured profile, and the whole market opens up.

Product

Scan or build your CV in Kormo; the parser turns paper into a profile. Jobs find you.

So we built the parser. The boxes became searchable profiles, and jobs started finding people. It worked — to a point.

One loopEscape Velocity

The air loop runs; the orbit loop closes.

Airborne · the harness loop

Build → verify → document

Fast, tireless — and amnesiac. Every run starts cold, corrections die with the run, and the 401st request costs exactly what the 1st did.

Orbit · the flywheel

Observe → nudge → compile → free

Every run teaches the next. Corrections accumulate, stable patterns leave the loop as hard code, and the model stays aimed at whatever is still unknown.

Same harness underneath. The difference is the loop feeds back into itself: the pipeline observes → context remembers and nudges the next guess → determinism compiles → the pipeline runs faster → the model is freed for new unknowns.
